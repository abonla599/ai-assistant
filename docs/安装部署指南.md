# AI智能助手 - 打包与部署指南（在线多租户版）

> **这份文档管的是什么，先说清。** 交付物只有一个：跑在这台 Windows 上的
> `dist\run_backend\run_backend.exe`。它同时端出 API 和网页界面——
> `backend/app/main.py` 里 `mount_pwa(app)` 把 PWA 挂在 `/app`、`mount_admin(app)`
> 把管理员页挂在 `/admin`，两边都是**同一个进程**（`backend/app/web/web_router.py`，
> `html=True` 所以 `/app/` 直接就是 `index.html`）。
> 再由 Cloudflare 命名隧道把它暴露成 `https://ai.fenever.xyz`：ingress 只有一条业务
> 规则 `hostname: ai.fenever.xyz → http://127.0.0.1:8000`，加一条 `http_status:404`
> 兜底，配置在 `C:\<用户>\.cloudflared\config.yml`（**那个文件不在仓库里**，它在每台
> 机器自己的用户目录下）。
> 手机上有两种用法：**装 APK 壳**（它只是个指向 `https://ai.fenever.xyz/app/` 的
> WebView，见 `android/app/build.gradle` 的 `buildConfigField APP_URL`），或者
> **浏览器直接开那个地址**。界面由服务端下发，所以改版不需要任何人重装。
>
> **桌面客户端那条路已经否决并删净了。** 仓库里没有 `flutter_app/`，`dist/` 下只剩
> `run_backend/` 一个目录；那条路专用的 `start_ai.bat`、`installer.nsi`、
> `create_portable.ps1`、`nginx\ai-chat.conf` 也已经一并删掉。
> 为什么"多一个启动脚本"这种事值得动手删而不是注释掉：`start_ai.bat` 和
> `tools\start-ai-stack.bat` 是两个都会去拉 `run_backend.exe` 的入口，两个人各跑一个
> 就有两个后端抢 `:8000`；抢端口会失败，但**换了端口就正好撞上最坏的那一种**——两个
> 进程同写一份 `data\` 与 `chroma_db\`，后写者把先写者刚追加的那条覆盖掉且**没有任何
> 报错**（见下面「一个数据根目录只允许一个服务进程」）。留着它不是冗余，是留一个会
> 静默损坏数据的开关。同理，NSIS 打包的是那个已经不存在的前端。

## 📋 前置要求

### 必需

1. **Python 3.12**
   ```powershell
   python --version
   ```
   钉在 3.12 不是随手写的：`.github/workflows/tests.yml` 把 CI 的解释器从 3.10 改成
   `'3.12'`，理由就写在它自己的注释里——这批代码全是在 3.12 上写、在 3.12 上验、并按
   3.12 打成 EXE 的，CI 曾是"唯一没被对齐过的那一环"。

2. **PyInstaller**（**只装在 PATH 上那个全局 Python 3.12 里，venv 里没有**）
   ```powershell
   venv\Scripts\python.exe -m PyInstaller --version   # → No module named PyInstaller
   python -m PyInstaller --version                    # → 6.20.0（全局那份）
   ```
   2026-09-19 实测就是这两行结果。这意味着**打 EXE 用的依赖集和跑测试用的依赖集不是
   同一份**：测试在 `venv\` 里跑，EXE 用全局解释器打。所以别以为 `venv` 绿了就等于
   产物是对的——这也是"判断构建成功只看产物，不看退出码"的另一半理由（见步骤 4）。
   顺带一句：仓库根 `requirements.txt` 与 `backend\requirements.txt` 是两份东西
   （前者 UTF-16、后者 UTF-8；CI 只 `pip install` 后者），别把它们当同一个清单。

3. **一个已配好的 Cloudflare 命名隧道**
   `tools\cloudflared.exe` 与 `C:\<用户>\.cloudflared\`（`config.yml` + `cert.pem` +
   那个 UUID 的 `*.json` 凭据）**都不在仓库里**。`.gitignore` 有一条 `/tools/` 整目录
   排除，注释写着"本地工具产物：cloudflared.exe、隧道 yml、启动脚本都不属于源码"。
   所以换一台机器，这一层是**照着本文自己重建**的，不是 `git clone` 下来就有的。

### 不需要

- **Flutter SDK / Visual Studio 的"C++ 桌面开发"负载 / NSIS**——它们属于上面那条已经
  删掉的路。
- **Android SDK**——出 APK 一律在 GitHub Actions 上跑。`build-apk.yml` 头部注释写的
  就是这件事的理由："本机没有 Android SDK，也不打算为此装 1.5GB —— GitHub runner 自带"。
- **nginx**——本机没有这一层。TLS 与域名都终结在 Cloudflare，回源是隧道那条
  `http://127.0.0.1:8000`，中间没有反代可配。

## 🛠️ 打包与上线

一次完整的"改完代码让线上跟上"就是下面七步。**顺序有意义**：先测再停，是因为停服窗口
越长越可能被人撞上；先验产物再启动，是因为一个残废 EXE 起来之后会在 `:8000` 上占住
位置，你从公网看到的只有一个 502。

### 步骤1: 全量测试

```powershell
cd backend
..\venv\Scripts\python.exe -m pytest tests/ -q
cd ..
```

期望全绿。**判据是"0 failed"，不是某个条数**——总数随用例增减（2026-09-19 一下午就从
`493 passed` 涨到 `495 passed`，中间只是新增了两条断言）。要对照的话当时的基线是
`495 passed, 9 skipped, 1 xfailed`。那 9 条 skip 里
8 条是 `tests/conftest.py:238` 那批**真起容器**的用例（本机没有 Docker 守护进程就跳，
报的是 `Docker 守护进程不可用`），第 9 条是 `test_tools.py:84`——它依赖公网搜索且结果
不确定，刻意不当回归锁。**所以别拿"跳过 9 条"当问题，但也别拿它当"CI 上会一样"：**
CI（`tests.yml`）会先 `docker build -f docker/sandbox/Dockerfile` 再跑，那 8 条在 CI 上
是真执行的。

### 步骤2: 数清楚现在有几份后端在跑

```powershell
tasklist /FI "IMAGENAME eq run_backend.exe"
netstat -ano | findstr /R /C:":8000 " | findstr LISTENING
```

`tools\start-ai-stack.bat` 自己就会先查 `:8000` 再决定起不起（见步骤 5），但你在控制台
手敲 `python run_backend.py` 或双击别处的 EXE 时没人替你查。多于一条 LISTENING 就停下
来先搞清楚是谁——多出来的那一份正在写同一批 `data\*.json`。

### 步骤3: 停服

```powershell
:: 先看上一步拿到的是什么 pid，确认它是 run_backend.exe 再杀
powershell -NoProfile -Command "Stop-Process -Id <当前8000上的pid> -Force"
```

### 步骤4: 重建 EXE（用 `.spec`，不要在命令行重抄参数）

```powershell
python -m PyInstaller run_backend.spec --noconfirm
```

**必须走 `run_backend.spec`。** 老版文档教的
`pyinstaller --onedir --name run_backend --hidden-import uvicorn.logging ...` 会打出一个
"能启动但功能残缺"的 EXE，而 spec 里每一条看着啰嗦的设置都对应一次真实翻车：

| spec 里的这一条 | 漏掉的后果（原文照抄） |
| --- | --- |
| `collect_all("chromadb")` + `collect_all("chromadb_rust_bindings")` | chromadb 按字符串路径动态导入 `chromadb.api.rust`，原生实现在另一个包里，"静态分析两者都发现不了" |
| `collect_all("fitz")` | PDF 解析是函数内延迟导入，"漏收会让冻结版一上传 PDF 就 ImportError" |
| `hiddenimports` 里的 `'multipart'` | FastAPI 条件导入，"缺失会让附件上传直接崩" |
| `datas` 里那两个前端目录 | "漏一个的后果是『源码版全对、EXE 版 404』，而这条不会让任何测试变红" |
| `excludes` 里那串 torch/transformers/... | 不是省空间才做的：它们是被可选依赖链拖进来的死重，"合计约 600MB"（产物实测 229MB，就是排掉之后的数） |

还有一条不在 spec 里而在 `run_backend.py` 开头：入口必须以顶层包名 `app` 导入。写成
`from backend.app.main import app` 的话，EXE 照样起得来，但 `main.py` 里那圈
`try/except ImportError` 会把每个 `app.*` 失败**静默吞掉**——"结果是 EXE 能启动但
记忆/工具/智能体全部失效"。

```powershell
ls dist\run_backend\
```

只应有 `_internal\` 与 `run_backend.exe` 两项。**判断构建成功只看产物，不看退出码**
（这句话抄自 `docs/superpowers/plans/2026-09-17-security-questions-and-self-service-reset.md`
的验收步骤，它被写下来就是因为"PyInstaller 退 0"和"这份 EXE 好用"是两件事——上面表里
那几条漏掉的后果，没有一条会让任何测试变红）。

如果里面冒出 `.env`、`data\`、`chroma_db\` 中的任何一个，**别启动**，先把它挪回项目根
再重建。原因见下面「运行时数据落在哪、怎么搬」——`dist\run_backend\` 每次重建都会被
整体删除，写在那里等于写在一个注定消失的地方（2026-09-16 真实丢过一次数据）。

### 步骤5: 起服务 + 隧道

```powershell
tools\start-ai-stack.bat
```

这一条就是**开机自启跑的那个脚本**，手工敲它等价于注销再登录一次。它做两件事，各自带
幂等判断，所以重复点不会叠出第二份进程：

```bat
rem 已在 8000 上监听就跳过后端
netstat -ano | findstr /R /C:":8000 " | findstr LISTENING >nul 2>&1
if errorlevel 1 (
  powershell -NoProfile -Command "Start-Process -FilePath '...dist\run_backend\run_backend.exe' -WorkingDirectory 'C:\Users\34426\ai-assistant' -WindowStyle Hidden"
)

rem 命名隧道（固定域名 ai.fenever.xyz）
tasklist /FI "IMAGENAME eq cloudflared.exe" | findstr /I cloudflared.exe >nul 2>&1
if errorlevel 1 (
  powershell -NoProfile -Command "Start-Process -FilePath '...tools\cloudflared.exe' -ArgumentList 'tunnel','run','ai-assistant' -WindowStyle Hidden"
)
```

两个进程都是 **`-WindowStyle Hidden`** 起的，这一点 2026-09-19 改过，理由不是美观：
从前写的是 `start "标题" /MIN`，那等于给每个进程配一个**带关闭按钮的控制台窗口**——
顺手点掉那个 X 就是杀进程，而且死得毫无痕迹。今天两次"后端静默消失"（约 2.5 小时、
约 37 分钟）都是那个形状：自己的日志里没有 traceback、Windows 事件里没有崩溃报告、
机器也没重启过。现在这条与 `deploy\watchdog.ps1` 用的是同一个启动形状，两条路径不再有
第二套行为。

同一个文件里还有一条当天踩到的坑，值得记在这是因为它会让人白查半天：**`.bat` 里的
注释别写中文**。cmd.exe 按 OEM 代码页（本机 936）读批处理文件，UTF-8 的中文注释会被
错误解码，结果 cmd 能把 `rem` 后半截当命令执行——实测过一次：加了中文注释之后那条
`netstat` 守卫**整段没跑**。本文件的注释因此是 ASCII，说明性文字写在文档里。

EXE 是隐藏窗口起的，日志没人看得到，所以 `run_backend.py::_route_logs_to_file()` 把
stdout/stderr 接到了 `data\backend.log`（**追加**写，超 1MB 先滚一份 `.1`）。要看服务端
证据就看这个文件，不要去任务栏找窗口。

### 步骤6: 验收（两条 curl，各管一段链路）

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/app/     # 后端自己
curl -s -o /dev/null -w "%{http_code}\n" https://ai.fenever.xyz/app/    # 整条链路
```

- 第一条 200、第二条不是 → **隧道到后端这一段**断了。隧道的报错落在项目根 `named.log`。
  但**别拿"named.log 没动"当隧道没跑的证据**——它只在**源站打不通**时才写行（全文行型是
  `ERR ... Request failed ... originService=http://127.0.0.1:8000`）。2026-09-19 实测：
  后端活着时经隧道发一次 200 请求，该文件一字节没涨（停在 44,135 字节 / mtime 不变）；
  下午那段 502 期间它才随请求增长。**要找实时隧道日志，先看进程，别翻这个文件。**
- 两条都 200 → 手机上的两种用法都活了，不用重装任何东西。

**`named.log` 这个名字别记成"隧道会自己写它"。** 现网活着的那条命名隧道确实把日志写进
了它，但**没有任何脚本做这件事**：`tools\start-ai-stack.bat` 和 `deploy\watchdog.ps1`
起的都是裸的 `cloudflared.exe tunnel run ai-assistant`，既不带 `> named.log` 也不带
`--log-file`。也就是说这台机器上这条隧道是某次**手工**起的、并把日志指到了这个文件——
具体是哪一种指法查不出来了，但结论不受影响：**由脚本自动拉起的那条不写这个文件**，
它 `-WindowStyle Hidden` 起、没有控制台也没有重定向，输出等于没人看。找不到实时隧道
日志时先看进程，别翻一个不再被写的文件。

顺带一条真实的坑，2026-09-19 现场就有：`start-ai-stack.bat` 判"隧道活没活"用的是
`tasklist /FI "IMAGENAME eq cloudflared.exe"`——**只按进程名**。本机当时挂着的三份
`cloudflared.exe` 里只有一份是命名隧道，另两份是 quick 隧道残留：

```
70824  cloudflared.exe tunnel run ai-assistant                    ← 真的那条
70844  cloudflared.exe tunnel --url http://127.0.0.1:8000 ...      ← 残留
73612  cloudflared.exe tunnel --url ... --config tools/quick-only.yml  ← 残留
```

按名字找会"看起来有隧道"，而命名隧道可能早就没了 —— 于是自启脚本判断"不用起"，域名继续
502。`deploy\watchdog.ps1` 的 `Get-TunnelProcess` 已经改成按**命令行**匹配
`tunnel run <name>`，注释里写的正是这件事；`.bat` 那一条**没改**，它是登录时跑一次的
角色，撞上的概率低，但排障时要知道它说的是哪一句。

### 步骤7: 没有"安装包"这一步

以前这里有步骤 6「`makensis installer.nsi` 制作安装包」和步骤 7「验证安装包」。它们连
同 `installer.nsi` 一起删了，因为**没有任何东西需要安装**：界面走服务端，唯一的发布动
作就是上面那七步。要交给别人的只有两样——一个网址，和一个 APK（见下面「发布流程」）。

## 🔌 开机自启与崩溃守护

**开机自启的真身是 `tools\start-ai-stack.bat`**，启动文件夹那条快捷方式
（`shell:startup\AI智能助手 - 自动启动.lnk`）指向的就是它。2026-09-19 实测：

```powershell
$s = (New-Object -ComObject WScript.Shell).CreateShortcut(
  "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\AI智能助手 - 自动启动.lnk")
$s.TargetPath    # → C:\Users\34426\ai-assistant\tools\start-ai-stack.bat
```

卸载自启的方法写在那个脚本的第 3 行注释里：删掉 `shell:startup` 里的快捷方式，再删掉
脚本本身。

### 它只管"登录那一刻"，不管"进程后来没了"

`start-ai-stack.bat` 是**登录时跑一次就退场**的脚本，之后没有任何人负责"进程没了再拉起
来"。这个洞真实兑现过一次：`deploy/watchdog.ps1` 头部记着 2026-09-19 那次事故——
`run_backend.exe`（PID 89476）在 11:59:31 之后消失，`data\backend.log` 里没有任何
`Shutting down` / `Finished server process`，正常退出流程一步都没走；下一次有进程是
14:39:02（人工重启），**中间约 2.5 小时是无人知晓的停机窗口**。

### `deploy/watchdog.ps1`：脚本已落地，计划任务**还没注册**

脚本在仓库里（`deploy/watchdog.ps1`，是跟踪文件），它补的正是上面那个洞：单次巡检、
进程不在就拉起、拉起就记账、连续失败熔断（默认每小时最多 3 次），只启动从不杀进程，
判定"活着"看的是**可执行文件全路径**而不只进程名。日志 `data\watchdog.log`，状态
`data\watchdog-state.json`，都在已 gitignore 的 `data\` 下。

⚠️ **但它现在不在跑，别把它当成兜底。** 2026-09-19 实测：

```powershell
schtasks /Query /TN "AI助手-崩溃守护"    # → 系统找不到指定的任务
```

注册命令（以及 `-DryRun` 空跑、`/Run` 手动触发、`/Delete` 卸载）都写在那个脚本自己的
头部注释里，脚本里那一行也标着"请本人确认后执行"——**这一步是留给人拍的，没有自动化，
也不该自动化**。空跑那条对现网是安全的：只判断、只打印，不拉起、不写日志、不写状态。

## 🔐 多用户部署：凭据、鉴权模式、数据落点与排障

这一节是**把服务交给别人用之前**必须读完的部分。代码里的规则都在
`backend/app/core/authz.py`（模式与中间件）、`auth.py`（身份库：bcrypt 密码摘要、
三道固定找回题的答案摘要 `answer_hashes`、可撤销会话令牌）、
`auth_router.py`（注册、登录、自助改密与管理端点，加上那四本按真实来源计的账），
这里只讲运维要做的事。

### ACCESS_TOKEN 现在是什么

| | 旧含义 | 现在的含义 |
| --- | --- | --- |
| 它是什么 | 全站共用的那把访问口令，谁拿到谁就是"唯一用户" | **bootstrap 管理员凭据**（引导口令） |
| 解析成谁 | 所有人 | `default_user` / 用户名"本机管理员" / 角色 `admin` |
| 用途 | 每个请求都带它 | 1) 让本机 EXE 与**已经发出去的 APK** 不改配置继续可用；2) 管理员用 `/admin` 页与 `/v1/admin/*` 接口时的那把凭据 |

- 给新用户的不该是这把口令，而是**他自己用「用户名 + 密码」注册或登录换回来的个人
  令牌**（一台设备一枚，可单独撤销）。注册已经不需要任何前置条件，见下面限流那一节。
- 配置位置：项目根的 `.env` 里 `ACCESS_TOKEN=...`（**不是** `dist\run_backend\.env`，
  那个目录每次重建都会被删掉，见下面"数据落点"）。
- 换掉它 = 换 bootstrap 口令：老口令当场失效，所有靠它直连的客户端要一起改。
- **不要把它写进任何分发物**（APK、前端静态文件、日志、公开仓库）。本仓已经因
  `.env` 被跟踪导致 API Key 公开五个月付出过代价，这把口令是公开仓库情况下
  唯一真正的门。
- 管理员**不来自任何请求体**：只有两处能产生 admin——这把口令，以及运维手工把
  `data/users.json` 里某人的 `role` 改成 `"admin"`（逃生口）。API 没有写 role 的口子。

> **手工改 `users.json` 必须停服再改。** 身份库只在**启动时读一次**，运行期间不再
> 重读；而任何一次改动（注册、登录、停用、轮换令牌）都是把**内存里那份**整表
> 重写回文件。所以对着一台在跑的服务手改 `role`：改完当场没效果（服务看不到），
> 重启才生效，而如果在重启之前有人注册过**或登录过**，你那一处改动已经被整表覆盖
> 掉了——没有任何报错。正确顺序：**停服务 → 改文件 → 起服务**。
>
> 换成密码模型之后这条更容易踩到：登录也是写盘动作（要往那人的令牌表里追加一枚
> 摘要），而登录每天会发生很多次；旧模型里"没人注册"就能腾出一个安全的改动窗口，
> 现在没有这个窗口。

### AUTH_MODE 的两种取值

| 取值 | 行为 | 用在哪 |
| --- | --- | --- |
| 不配 / `enforced` / 任何未知取值 | 每条 `/v1/`（以及 `/docs`、`/redoc`、`/openapi.json`）都要凭据，匿名 401；文档路由**在启动时就不生成** | 任何可能被外人访问到的部署（**默认**） |
| `disabled` | 所有请求一律以**本机管理员**身份运行，启动时打印一行警告；文档路由照常开 | 只用于本机开发 |

判定只看字符串是否等于 `disabled`，写错（`dissabled`、`false`、空串）都落到
`enforced` 那一侧——**未知取值按安全侧处理**，这条有测试钉着。

### 没有凭据 = 503，不是"门开着"

`AUTH_MODE` 不是 disabled、`ACCESS_TOKEN` 为空、且 `data/users.json` 里没有任何
`role=admin` 的人 —— 此时服务端**一个可服务的身份都没有**，所有受保护端点直接返回
`503 {"detail":"服务端未配置访问凭据"}`。**这是刻意的 fail-closed**：忘配 env 绝不等
于把一台 API 公网敞开。免凭据的端点只有 `authz.PUBLIC_PATHS` 那三条——
`POST /v1/auth/register`、`POST /v1/auth/login`、`POST /v1/auth/reset`
（否则第一个身份永远注册不出来、第二个身份永远登不回来、忘了密码的人永远自救不了），
它们不依赖有没有配 admin。**没有第四条**：`1ff52a78` 那次确实做过一条"把这个人的找回
问题念给来人听"的 `POST /v1/auth/recovery`，本轮已整条删净（`app/` 里搜不到这个路径）。
理由是三道找回题现在是写在 `app/core/auth.py`（`RECOVERY_QUESTIONS`）里的全站常量、
前端自己渲染：问服务器要一句服务器抄出来的话，只是白白多开一条能回答
"这个用户名存在吗 / 他设过找回吗"的信道。

排障对照：

| 现象 | 意思 | 该做什么 |
| --- | --- | --- |
| `503 服务端未配置访问凭据` | 没配口令、库里也没有 admin | 在 `.env` 配 `ACCESS_TOKEN` 并重启；或手工往 `data/users.json` 写一个 `role: "admin"` 的人**并重启**（见下：不改完就重启等于没改） |
| `401 缺少或错误的访问凭据` | 有身份可服务，但**这个请求**没带或带错了令牌 | 让用户在首屏那层登录界面用用户名 + 密码登录一次（会发一枚新令牌）；确认不是管理员轮换过 |
| `401 用户名或密码不正确`（来自 `/v1/auth/login`） | 用户名不存在、密码错、**或账号被停用**——服务端刻意把这三句合成一句，且三种情况都付一次真实 bcrypt | 让用户核对用户名与密码；确定没输错就找管理员，这**不是**"令牌填错了" |
| `401 答案不正确`（来自 `/v1/auth/reset`） | 三道题没全对、这个用户名不存在、这个人**没留过答案**、或账号被停用——四种原因同一句话、同一份耗时 | 别去猜是哪一种（这个端点刻意不回答）；账号确实被停用就先 `enable`，没留过答案就只能删号重建 |
| `403 需要管理员权限` | 身份是真的，角色不够 | 普通用户本来就不该看到这些端点，别放开；要改配置请用管理员口令 |
| `409 该用户名已存在` | 注册撞名（实话，因为改名是用户自己能解决的事） | 换个用户名再点一次；这一格会计进该来源的失败预算 |
| `422 提交的内容不完整或格式不对：请检查每一栏都填了` | **请求体在 pydantic 那一层就读不通**：整个字段缺失、类型不对（`answers` 传成了字符串）、不是对象。由 `app/main.py` 的 `on_malformed_body` 统一压平，字段路径只进服务端日志（`⚠️ 请求体形状不对（body.password）`），不回客户端。**注意：这不是"整站唯一的 422"**，存储层那三种见下一行 | 看服务端日志那一行定位是哪一栏；这一类是手滑，**不烧任何账本** |
| `422 找回的 3 题答案都要填，且每题至少 2 个字符` / `422 密码至少 8 位` / `422 用户名最长 24 个字符` | **请求体读得通、但值不合格**：这些是存储层 `app/core/auth.py` 的形状闸门（`_check_answer_shapes` / `_check_password_shape` / `_normalize_username`）说的，它跑在读库与比对**之前**，所以回的既不是上面那句、也不是 `答案不正确`。「条数不对」（只交了两条答案）走的也是这里，不是上面那一行 | 照着那句话改对应的那一格就行；同样**不烧任何账本**（判据：`test_auth_endpoints.py` 里的 free_typo 与"数错格子不计费"那两条） |
| `429 尝试次数过多` | 命中四本账之一（见下一小节）：`Retry-After` 给的就是那一本的窗口 | 看 `Retry-After` 决定等多久；24 小时那两本要等到明天。校园网/运营商出口是**共享 IP**，先确认不是自己人把预算用完了 |
| 前端显示"服务端还没有可用的模型，请联系管理员配置模型服务"（`app.js` 的原话，另两句见 `当前没有可用模型，请在「设置 → 模型服务」中配置`） | 项目根的 `.env` 没被读到，或 provider 一条没配 | 检查 `.env` 在不在**项目根**（不是 dist 里），再看 `/v1/models` 的 `usable` |

### 真实访客 IP 限流：注册已经开放，只剩这一道闸门

邀请码那一层整体删掉了：`data/invites.json`、`tools\make-invite.bat`、以及
`POST/GET/DELETE /v1/admin/invites*` 三个端点都不存在。**任何人只要知道地址，就能用
自己起的用户名 + 自设密码注册一个账号，不需要管理员参与。** 挡在中间的只剩四本账，
键都是**真实访客 IP**（`core/auth_router.py`，清单就是那份 `_LEDGERS`）：

| 账本 | 阈值 | 记什么 | 谁能清它 | 命中之后 |
| --- | --- | --- | --- | --- |
| `_FAILS` | 每来源 10 次 / 600 秒 | 登录失败（401）**以及**注册撞名（409）——两件事共用同一格预算 | **谁都不能清**（终审 F3 删掉了 register/login 成功时的 `_FAILS.pop(ip)`），只有窗口自己过期 | `/v1/auth/login` 与 `/v1/auth/register` 返回 `429`，`Retry-After: 600` |
| `_REGISTERS` | 每来源 3 次**成功** / 24 小时 | 注册成功 | 没人清，只有窗口自己过期 | `429`，`Retry-After: 86400`：今天这个来源再注册不了 |
| `_RESET_FAILS` | 每来源 10 次 / 600 秒 | 自助改密被拒（`401 答案不正确` 那四种原因同一格） | **谁都不能清**：登录成功、注册成功、改密成功都不行 | `429`，`Retry-After: 600` |
| `_RESETS` | 每来源 3 次**成功** / 24 小时 | 改密成功 | 没人清，只有窗口自己过期 | `429`，`Retry-After: 86400` |

- 为什么第二本账记"成功"而不是记失败：撞名是零成本的，一个脚本可以无限撞名而一个号
  也建不出来；真正花钱的是"注册成功 + 拿去向模型发请求"。改密那两本同理——
  三题的题目是全站公开的常量，"答对"并不说明对面是本人，只说明他猜中了；而每一次
  成功都把名下**所有**会话令牌作废，对被猜的人而言每台设备都掉线是真实的伤害。
- 为什么撞名要计进失败账本：过去"这个名字存不存在"是藏在邀请码后面的实话，现在它
  前面没有门了，所以每问一次就扣一格登录预算——脚本要每 10 次换一枚真实访客 IP。
  **这句从终审 F3 起才真的成立**：那时删掉了 `register` / `login` 成功路径上的
  `_FAILS.pop(ip)`，脚本再也不能靠"自己的号成功一次"把账洗掉。
- **为什么猜答案的失败要单独一册**：现在留着的是两条——① 猜口令与猜三题是两种不同的
  猜测面，共用一格预算时一个人猜错九次之后连自己的密码都不许再试一次；② 429 落在哪本
  账上要看得出来（`Retry-After` 是 600 还是 86400），否则运维分不清刚才被挡的是枚举
  用户名还是在猜找回答案。`/v1/auth/reset` 因此**只看两本**（`_RESET_FAILS`、
  `_RESETS`），`_FAILS` 它既不看不写。当初拆账的**首要**理由——"`_FAILS` 会被一次成功
  登录洗掉，所以猜答案的人随手就能拿到免死金牌"——已经随 F3 一起消失了；判据
  （`test_no_other_success_pays_off_the_guessing_ledger`）不依赖那句也照样要成立。
- 不计进任何账本的失败：用户名为空/超长/保留字/含不可见字符、密码不足 8 位、
  三条答案有空格或太短（都是 422）。那是当事人改一下就过的手滑，算进预算只会让
  唯一的登录入口被自己的用户锁死。
- **没有任何成功能还回预算**（终审 F3）：`_FAILS`、`_RESET_FAILS` 两本失败账都只进不出，
  只有窗口自己过期才松。旧行为是"一次成功登录或注册把该来源的 `_FAILS` 清零"，实测
  它保护的不是真人：一台机器穿插自己的号，撞名枚举跑到 45 次 409 / 0 次 429、口令猜测
  36 次错 / 0 次 429。代价如实认：**同一个十分钟窗口里连续打错十次的真人要等窗口过去**
  （话术是"尝试次数过多，请稍后再试"，`Retry-After: 600`），共享出口下更容易撞到。
  本项目在安全取舍上一贯选安全侧（fail-closed、可撤销、查无此人 404），这一条跟着那条走。

**这把锁挡得住什么、挡不住什么：**

- **挡不住手里有很多出口 IP 的人。** Cloudflare 把访客 IP 交得很实，用拨号池或代理
  列表的脚本每枚 IP 都有崭新的 3 个号 + 3 次改密。注册开放之后就不存在"按人限速"
  意义上的防线了，这里只是把单机脚本的成本抬上去。
- **会挡到共享出口的正当用户。** `CF-Connecting-IP` 是"出口"不是"人"：校园网 NAT、
  运营商 CGNAT 后面成百上千人共用一个公网地址，于是 3 个/天意味着同出口第四个人
  当天下不来号；同一出口里两个人当天各改一次密码，第三个人就只剩一次。这是按 IP
  计费的必然代价，别指望它公平；它只保证"一个来源刷不出几百个号"。
- 接受这一切的理由只有一个：**模型 API Key 是运维自己掏的钱**。注册开放等于任何人都
  能消耗那份按 token 计费的额度，所以这道闸门本质是**账单闸门**，不是入侵检测。
  真要把门关严，办法是别把地址公开传播（发到只有认识的人的群里），而不是调阈值。

来源 IP 怎么取的（`auth_router._client_ip()`）：**先读 `CF-Connecting-IP`，取不到才
退回 `request.client.host`；`X-Forwarded-For` 刻意不信**——那是一条可以被追加的链，
取首项等于取攻击者写的第一句假话。这份信任的前提是部署事实：域名必经 Cloudflare、
后端只听 `127.0.0.1:8000`、外部没有旁路。**这个头是被无条件信任的**，所以哪天 8000
能被外网直连，任何人都能随手编一个 IP 拿到全新预算，上面所有结论当场作废。换别的
隧道或 CDN 时，要么让它写同一个头，要么就接受"全网共用一格"——旧版文档教的
`--proxy-headers --forwarded-allow-ips` 对本服务**无效**，因为它读的从来不是
`X-Forwarded-For`。

还剩三条要说明的（都是取舍，不是待修的 bug）：

1. 四本账都是**进程内**的字典：重启即清零，多开一个 worker 就是各记各的。可以接受，
   因为真正的凭据校验是 bcrypt + 至少 8 位密码；但别把它当审计日志。
2. 账本有个 4096 个来源的上限（`MAX_TRACKED_SOURCES`），超了之后 `_prune` 丢的是
   **整桶都已过期**的键，而且**每本账按自己的窗口过**——十分钟的尺子不会去量 24 小时
   那两本。这一条本轮修过一次：修之前压力下今天的注册/改密计数会被提前清掉，
   那是配额被悄悄放宽（fail-open）。所以它的当前形状是"尖峰时最多丢掉已过期的条目，
   不会把还没到窗口的配额松开"，判据在
   `tests/test_auth_endpoints.py::test_prune_uses_each_ledgers_own_window`。
3. `/v1/auth/login` 与 `/v1/auth/reset` 都是公开端点，而"查无此人"那一支**也**要跑真实
   bcrypt（对着固定摘要 `_DUMMY_PW_HASH`；找回那一路是三枚，每题一枚），否则响应快慢
   本身就是一份用户名名单。于是不必猜中任何密码，任何人只要发足够多的登录或改密请求，
   就能按每次几十到几百毫秒的量吃这台机器的 CPU。这是"几种失败同一句话"所付的代价，
   目前没有东西替它兜底。

### 运行时数据落在哪、怎么搬

**一个数据根目录只允许一个服务进程。** 这些存储（sessions / users /
providers / uploads / feedback / preference / chroma_db）内部用的是**进程内**的
`threading.Lock` 加"整份读出来、改一下、整份写回去"的写法：同一个进程里的并发是安全的，
**两个进程同时写同一份文件就会互相覆盖**——后写者手里的旧全表不包含先写者刚追加的那条，
写回去那条就凭空消失，而且没有任何报错。最常见的两种翻车方式：

- 桌面上的 EXE 已经在跑，运维又开一个控制台手动 `python run_backend.py`（端口撞了会失败，
  但换了端口就正好撞上这一条）；
- 开机自启了一份，手工测试时又起了一份。

要确认现在到底有几份进程在写：数 `run_backend.exe` 的进程数，或者看启动日志里那一行
`📁 可变运行时数据` 打出的路径是不是同一棵（见下）。

服务**启动时会把七份数据的绝对路径各打一行**（`backend/app/core/paths.py::
log_data_locations`），落在 `data\` 之外的还会单独点名：

```
📁 可变运行时数据（项目根 C:\Users\you\ai-assistant）：
     会话           C:\Users\you\ai-assistant\data\sessions.json
     身份库         C:\Users\you\ai-assistant\data\users.json
   ↳ 长期记忆向量库 C:\you\other-disk\chroma_db   ← 由环境变量 CHROMA_DB_PATH 指走
   ⚠️ 偏好摘要      C:\Users\you\ai-assistant\preference.txt
                                                     ← 不在 data/ 之下：读的是项目根那份
                                                        历史数据（用 PREFERENCE_FILE 可指走）
   ⚠️ 一个数据根目录只允许一个服务进程：…
```

之所以要把它打印出来而不是只写在下面这段散文里：`data_file()` 在 `data\` 下**没有**同名
文件时会退回项目根那份历史文件，所以"我的数据是不是都在 data\ 底下"取决于本机有没有一个
老 `preference.txt`——光读文档猜不准，看一眼启动日志就知道。

一切**可变数据**都挂在**项目根**（`backend/app/core/paths.py::data_root()` 单点提供）：

```
<项目根>\data\sessions.json      会话
<项目根>\data\users.json         身份库（密码与三道找回题答案都是 bcrypt 摘要 `pw_hash`/
                                 `answer_hashes`、会话令牌是 SHA-256 摘要，都不是明文；
                                 备份它等于备份一份"能改别人密码"的原始材料）
<项目根>\data\providers.json     模型服务配置（含密钥）
<项目根>\data\uploads\           附件
<项目根>\data\feedback.json      反馈原文
<项目根>\data\preference.txt     偏好摘要（本机管理员那份）
<项目根>\data\preference-<uid>.txt  其余每个人的偏好摘要
<项目根>\chroma_db\              长期记忆向量库
```

- **绝不能落在 `dist\run_backend\`**：PyInstaller 重建会**整体删除**该目录
  （2026-09-16 真实丢过一次数据）。构建完必须复查 `dist\run_backend\` 只剩
  `_internal\` 与 `run_backend.exe`；重建前先 `ls dist\run_backend\` 确认里面没有
  `.env`、`data\`、`chroma_db\`。
- 每一份都可以用环境变量指走（放别的盘、测试隔离都靠它）：
  `SESSION_DB_PATH`、`USERS_DB_PATH`、`PROVIDERS_DB_PATH`、
  `UPLOAD_DIR`、`CHROMA_DB_PATH`、`FEEDBACK_FILE`、`PREFERENCE_FILE`。
  优先级：**环境变量 > `<项目根>\data\<文件>` > `<项目根>\<文件>`（历史兼容）**。
  老部署的 `data\invites.json` 现在没人读了（服务不会删它，也不会因为它报错）；
  确认不需要留档就可以手工清掉，`INVITES_DB_PATH` 也已经没有任何代码看它。
- 老版本把 `feedback.json` / `preference.txt` 直接写在**项目根**。服务仍会读那两份
  （不会丢历史），但要收进 `data\` 才与其它数据同源。搬法（**先停服务**）：

  ```bat
  move feedback.json data\feedback.json
  move preference.txt data\preference.txt
  ```

  ⚠️ **这一步要和"重建 EXE + 重启服务"同批做。** 正在跑的那份 `run_backend.exe`
  早于本次改动，它写死的还是项目根那两份；只要它还在线服务，搬走文件它就照着老路径
  **再在根上写一份**，历史当场裂成两半。正确顺序：停服务 → 重建 → 搬文件 → 启动。

  搬完重启，日志里偏好摘要那行应显示 `data\preference...txt`。**别两边各留一份**：
  `data\` 下存在时以它为准，根目录那份从此不会再被写。
- 这些文件都在 `.gitignore` 里（且用的是 glob 形状，`preference*.txt` 一并兜住按人
  分账后的新文件名），**不要提交**。

### 管理员的第一件事：打开 `/admin`

已经没有"签发第一个邀请码"这一步了（`tools\make-invite.bat` 连同三个
`/v1/admin/invites*` 端点一起删掉，用户自己注册）。装机之后管理员要做的动作只有三下：

```bat
:: 1. 项目根 .env 里配好 ACCESS_TOKEN（留空且库里没有 admin 会一律 503，见上文）
:: 2. 起服务 —— 用自启那条脚本，别直接双击 dist\run_backend\run_backend.exe：
::    开机已经起过一份的情况下，双击会第二份，端口撞了会失败，换端口就正好同写一份数据
tools\start-ai-stack.bat
:: 3. 浏览器打开 http://127.0.0.1:8000/admin/ ，在口令框里填那把 ACCESS_TOKEN
```

`/admin` 由**同一个进程**挂出来（`backend/app/web/admin/`，与 PWA 共用一份样式）。
它是个**不含数据的空壳**：整页只有 HTML 与 JS，一个用户名都不写死；列表和所有动作都要
在页面上点，走的仍是 `/v1/admin/*` 那套 `require_admin` 接口。所以这个地址公开是刻意
的——`/admin` 也确实不在鉴权保护前缀里，这条有 `backend/tests/test_admin_page.py` 钉着。
口令只存在这台浏览器的 localStorage，不进 URL、不进日志。

页面上能做的就四类：列用户（含每人的**设备数**与最后活跃）、停用/恢复、换发令牌、删人。
不想开浏览器时，下面"日常四条"的 curl 是同一批接口。

- **`role` 只能手工改出来。** 想把别人也变成 admin，唯一的路是**停服**把
  `data\users.json` 里那人的 `role` 改成 `"admin"` 再重启（见上文"必须停服再改"）。
  页面与 API 都没有这个口子：开一个能写 role 的接口，等于把整套身份体系作废。
- 换发出来的新令牌**只在响应里出现一次**，所以页面把它做成必须主动确认的弹窗——
  关掉窗口就再也取不到明文，只能再轮换一次，而代价是全端重登。

### 管理员日常四条

```bash
curl -H "Authorization: Bearer $ACCESS_TOKEN" http://127.0.0.1:8000/v1/admin/users
curl -X POST -H "Authorization: Bearer $ACCESS_TOKEN" http://127.0.0.1:8000/v1/admin/users/<user_id>/disable
curl -X POST -H "Authorization: Bearer $ACCESS_TOKEN" http://127.0.0.1:8000/v1/admin/users/<user_id>/enable
curl -X POST -H "Authorization: Bearer $ACCESS_TOKEN" http://127.0.0.1:8000/v1/admin/users/<user_id>/rotate-token
```

- `disable` **当场**让那人名下全部令牌失效，而且**密码填对也登不进来**（登录对停用账号
  回的就是"用户名或密码不正确"那一句，与密码错逐字节相同）；`enable` 是可逆的那一半，
  恢复后**原有令牌继续可用**（轮换不会顺手解除停用，两件事各管各的）。
- `rotate-token` 是**强制全端重登**：它先把那人的令牌表整个清空，再发一枚新的。有了
  多设备并存（一人最多同时留 8 枚，超了丢最老的）之后，"只换掉其中一枚"等于什么都没
  撤销——别人手机那枚还能用。所以这里的"撤销"必须是全部。
- `GET /v1/admin/users` 只给一个 `sessions` **数量**，永远不回报令牌摘要：摘要是凭据。
- `DELETE /v1/admin/users/<user_id>` 删人，不能删自己。
- **用户忘记密码走自助，不走您**：注册第二步留的是**三道全站固定题**的答案
  （你的手机号后四位是什么？/ 你小学在哪上？/ 你父母姓氏的拼音首字母各一个是什么？——题目在
  `app/core/auth.py:RECOVERY_QUESTIONS`，人人同一份），登录页点「忘记密码」后是
  **两个屏幕**：先输用户名，再一次交出三道答案 + 新密码 + 确认新密码；提交成功的第三
  "步"是界面自动回到登录。答案与密码同样是 **bcrypt 摘要**（它往往是个能猜的地名，熵
  比密码还低，所以绝不能只存快哈希），而**题目本身不进库**。改密成功的后果包括
  **清空那人名下所有令牌**——每台设备都要重新登录，这是设计而不是 bug（界面上那句
  「密码已重置，请用新密码登录。其他设备需要重新登录一次。」说的就是它）。
- 免凭据端点因此是 **3 条**：`/v1/auth/register`、`/v1/auth/login`、`/v1/auth/reset`，
  全部由 `tests/test_route_auth_contract.py` 逐个点名钉住（多一条少一条都红）。
  设想过、也短暂存在过的那条 `/v1/auth/recovery`（"把问题念给我听"）已删除：
  题目是常量，那条信道只会白白回答"这个用户名存在吗、他设过找回吗"。
  `reset` 的防线：答案与新密码**一次提交**（分开验答案就等于给外人一台"这一句对不对"
  的机器）；三道**全对**才放行、比对**不短路**（三枚 bcrypt 全跑完再判，否则"第几题猜对了"
  漏在耗时里）；新密码的形状**先于**答案校验；四种失败（查无此人 / 没留答案 / 答案错 /
  已停用）**同一句话、同一形状、同一耗时**；手滑类不合格是 422 且不记账。
- **答案也忘了就是终局**：没有邮件/短信通道，也没有重置链接，您手里仍然只有停用、
  轮换、删号三件事。别急着补一个"管理员代改密码"的接口：**能替别人设定凭据的接口一个
  都没有**（`/v1/admin/users/*` 只有 disable / enable / rotate-token / DELETE 四种，
  `role` 也只能停服手改），这正是它不该存在的原因。所以手册里那句"填一个多年后还记得
  的答案"不是玩笑话。
- ⚠️ **`data\users.json` 此刻躺着三个试验身份**（2026-09-19 实读）：`实验账号1`（0 枚令牌）、
  `试验二号`（3 枚）、`试验三号`（1 枚）。它们**都是完整的**——每条都带 `pw_hash` 与三枚
  `answer_hashes`，所以自助重置、登录、换发令牌都照常工作，不存在"坏号"要修。
  要不要清由你定：确认无人使用就在 `/admin` 页逐个删除（等价于
  `DELETE /v1/admin/users/<user_id>`），**别写脚本去改这份真实数据**，也**别**手工回填
  `answer_hashes`——那等于凭空造出一份没人知道的找回凭据。
  删号只删身份记录这一条限制写在上面（会话/附件/记忆不级联）。
  历史上这里还躺着过 `老李`、`实验1号`、`实验一号` 三条**残缺**记录（没有 `answer_hashes`、
  其中两条连 `pw_hash` 都没有），那才是"自助重置对它们永远只回那句「答案不正确」"的成因——
  三条已于那轮"删除试验账号"里清掉（`data\users.json` 不被 git 跟踪，所以这里给不出提交号），
  留一句是为了让读到"报错分不出'没设'和'答错'"这个设计的人
  知道它防的是哪种数据。

## 📦 发布流程

这里有**两条互不相同**的发布路，别混：后端那条不发文件，安卓那条才发文件。

### 后端（界面、API、模型配置）：不发任何东西

发布 = 「上面打包七步」+ `git push`。用户那边没有"更新"这个动作：界面由服务端下发，
下一次打开 `https://ai.fenever.xyz/app/` 加载的就是当前那一版。

> 这条不是推测，是 `web_router.py::RevalidatingStaticFiles` 的存在理由：它给 `/app` 与
> `/admin` 下每个响应都盖 `Cache-Control: no-cache`。原因写在它的 docstring 里——
> 源站原先不表态，Cloudflare 就替它填了 `max-age=14400`，于是 2026-09-17 重建重启之后
> 公网拿到的还是 80 分钟前那份 `style.css`（`cf-cache-status: HIT`），改版在用户那边
> 变成"改了没生效"。**没有这条，"不用重装"就是假话。**

### 安卓壳：改版本号 → 打 tag → CI 出 Release

APK 只是指向那个网址的 WebView 壳，所以只有**改壳的功能**才需要发版（提醒、分享入口、
桌面组件那三类是壳自己的，见 `release-apk.yml` 生成的 Release 说明）。

```bash
# 1. 先改版本号：android/app/build.gradle 是这台机器上包版本的**唯一来源**
#    （当前：versionCode 13 / versionName "0.13"）
#    versionCode 必须一起涨，否则老手机装上就**覆盖不掉**。

# 2. 提交、推 develop（本仓日常在 develop 上走，不并 main）
git add android/app/build.gradle
git commit -m "v0.14：版本号升到 14"
git push origin develop

# 3. 打 tag 并推上去 —— 这一步就是发布动作本身
git tag v0.14
git push origin v0.14
```

`.github/workflows/release-apk.yml` 由 `push: tags: ["v*"]` 触发，之后全自动：

- **先校验 tag 和 `versionName` 必须一致**，不一致直接 `exit 1`。注释写了为什么钉这条：
  对不上就"事后谁也说不清用户装的到底是哪一版"。**所以 versionName 忘了改 = CI 红，
  而不是发了个错版。**
- `gradle -p android assembleDebug` 出**调试包**——`build-apk.yml` 的注释说明为什么是
  debug：Android 自动用 debug keystore 签名，装上即用，本仓不养发布密钥。
- 产物改名成 `ai-assistant-0.14.apk` 后用 `gh release create` 发到公开 Release，
  标题 `AI 助手 0.14（安卓）`。**`gh` 跑在 runner 上**（本机没装 gh CLI，2026-09-19 实测
  `which gh` 找不到），用的是 workflow 自带的 `GITHUB_TOKEN`（`permissions: contents: write`）。
- 失败要重跑：`workflow_dispatch` 手动触发即可，它保留原 tag，所以 `GITHUB_REF_NAME`
  还是 `v*`，那条一致性校验照样成立。

发完之后给别人的是一句"点开这个链接下载 apk"，而不是一个安装包文件。Release 说明里那
三条安装步骤（含"禁止安装未知来源应用"要去**设置 → 应用 → 允许来自此来源的安装**勾选一次）
是 workflow 里的 heredoc 生成的，不在本文维护范围内。

## ⚠️ 注意事项

### 常见问题

1. **公网 502，本机 `:8000` 没人监听**
   先分清是"没起来"还是"起来了但没起来对的东西"：
   ```powershell
   netstat -ano -p TCP | findstr ":8000.*LISTENING"
   Get-CimInstance Win32_Process -Filter "Name='cloudflared.exe'" |
     Select-Object ProcessId,CommandLine      # 看命令行，别看进程名
   ```
   隧道在、后端不在 → 就是登录自启之后进程死掉那种（见「开机自启与崩溃守护」）。
   **而唯一会拉它起来的 watchdog 目前还没注册成计划任务**，所以现网这一步得人来。
   `data\backend.log` 里若没有 `Shutting down` / `Finished server process`，那是被硬杀
   或崩了，不是正常退出。

2. **PyInstaller 打包后缺少模块 / EXE 起来但功能全废**
   **不要**回到命令行去补 `--hidden-import`。补进 `run_backend.spec`：那张表里每一项都
   是一次真实翻车（见步骤 4 的表）。判据不是"有没有报错"，而是"EXE 起得来但功能不亮"——
   `main.py` 那圈 `try/except ImportError` 会把导入失败逐个吞掉，`datas` 少一个前端目录
   也不会让任何测试变红。

3. **重建之后长期记忆/会话/模型配置全空**
   说明它们被写在了 `dist\run_backend\` 里，而那次重建把整个目录删了
   （2026-09-16 真实丢过一次）。所有可变数据必须在**项目根**，见「运行时数据落在哪、怎么搬」。
   构建完第一件事就是 `ls dist\run_backend\` 确认只有 `_internal\` 与 `run_backend.exe`。

4. **两个后端抢 `:8000`，或者更糟：数据互相覆盖**
   端口撞了会起不来（这是运气好）；换了端口起来才是事故——两个进程各拿一份内存整表往
   同一批文件回写，后写者抹掉先写者刚追加的那条，没有报错。查法：数 `run_backend.exe`
   的进程数，或对一眼启动日志里 `📁 可变运行时数据` 打出的路径是不是同一棵。
   防法：入口**只有一个** `tools\start-ai-stack.bat`，它自带 `:8000` 幂等判断。

5. **APK 装上后仍是旧壳**
   `versionCode` 没涨。CI 只校验 tag 与 `versionName` 一致（`release-apk.yml` 那一步），
   **没有任何东西替你校验 `versionCode` 递增** —— 那是 Android 安装期的行为，出了门才发现。

`start_ai.bat`、`installer.nsi`（连同 `makensis` 那两步与 `AI智能助手_Setup.exe`）、

## 🔒 安全建议

1. **`.env` 不在仓库里，这件事靠 `.gitignore` 兜**（它已经有 `.env` 这一条）。真正要盯的
   是形状：`.gitignore` 顶部注释记着本仓的教训——`chroma_db/` 与 `.env` 曾被跟踪，一把
   API Key 因此公开了五个月；而"漏一个名字就裸奔"正是那种事故的形状，所以那批条目用的是
   glob（`preference*.txt` 才兜得住按人分账后的 `preference-<uid>.txt`）。**加一份新数据
   文件时改的是那张 glob，不是往提交里赌。**

2. **`.env.example` 是给运维抄成项目根 `.env` 的模板，不是发给用户的东西**：填它的人是
   **在这台机器上装服务的那个人**，填的是模型密钥与那把 bootstrap 管理员口令。普通用户
   全程不碰任何密钥——他们只填「用户名 + 密码」，见上面 ACCESS_TOKEN 那一节（`.env.example`
   自己的注释也这么写：「任何用户都不该被要求填 ACCESS_TOKEN」）。老措辞"让用户自行填写
   API密钥"就是这个动作的假话版本。

3. **`ACCESS_TOKEN` 是 bootstrap 管理员口令**，不是"分享码"：别写进 APK、前端静态
   文件或任何公开产物里，也不要发给用户；用户用的令牌一律是他们自己拿
   「用户名 + 密码」换出来的**可撤销个人令牌**。注册开放之后这把口令比过去更要看好
   ——拿到它的人既能改写模型服务配置（含密钥），也能列人、停人、删人。

4. **免凭据的公开面只有三个端点**（`/v1/auth/register`、`/v1/auth/login`、
   `/v1/auth/reset`），名单就是 `authz.PUBLIC_PATHS`。往那里加**第四条**会当场让
   `backend/tests/test_route_auth_contract.py` 变红——那是刻意的，不是测试太严。
   本轮删掉的正是一条曾被设想、也短暂存在过的第四条（`/v1/auth/recovery`，"把找回问题
   念给来人听"）：三道题是写在 `app/core/auth.py` 里的全站常量，那条信道唯一还能回答的
   就是"这个用户名存在吗、他当年留没留找回答案"这两比特。**多出来的这一条 `reset` 的代价**（找回答案是
   可猜凭据、同一来源每窗口 10 次猜口令 **加** 10 次猜答案、改密成功会踢掉本人所有设备）
   逐条记在设计文档
   `docs/superpowers/specs/2026-09-17-credentials-and-self-service-reset-design.md` §6。

5. **签名这件事只针对 APK，不针对 EXE。** EXE 从不离开这台机器（`dist/` 整目录
   gitignore，也没有安装包对外发过），所以 Windows SmartScreen 那条路在当前形态下不存在，
   给它买代码签名证书没有对象可签。真正会被系统拦一下的是**调试签名的 APK**：
   `build-apk.yml` 明说选 debug 是为了"Android 自动用 debug keystore 签名，装上即用"，
   代价就是用户安装时会看到"禁止安装未知来源应用"那一屏，要他去
   **设置 → 应用 → 允许来自此来源的安装**勾一次。这句提示词就写在 `release-apk.yml`
   生成的 Release 说明里，别在别处另发明一套说法。
