三屏的取证手法相同：本机起后端（隔离数据目录、`AUTH_MODE=disabled`）+ 无头 Edge 走 CDP

## 二之四、R1 实测抓到并已修掉的一个真缺陷（不是端差异，是 bug）

**症状**：这台设备从没登录过、但服务端认得出人（`AUTH_MODE=disabled` 的本机管理员，
或将来任何"凭据有效而本机清单为空"的走法）时，网页版聊天**看着正常、其实全丢**。

**取证过程**（`_local_verify/r1.json` 是修复前的原始输出）：

| 观察点 | 修复前实测 | 修复后实测 |
|---|---|---|
| `state.me` | `default_user / admin`（服务端认人） | 同 |
| 本机身份清单条目数 | **0** | 1 |
| `pref.sessionId`（发完两轮之后） | **空串** | 稳定一个 uuid，两轮不翻 |
| 服务端会话条数 | **2 条**（每发一条消息各建一条） | 1 条 |
| 服务端会话正文 | **两条都 0 句**（正文一个字没上去） | 4 句，角色序列 `u/a/u/a` 与界面一致 |
| 刷新之后 | 屏幕空着且不报错 | 从服务端读回并渲染 |
| R2 导出 | 拼出 `/v1/sessions//export-ticket`，永远换不到票 | 真点导出走到签票 + 兑换（见第二节之三） |

**根因**（一句话）：`patchCurrent()` 第一句 `if (!hit) return;` 是静默的，而身份条目只在
登录/注册/手工录入凭据三处才写（`addIdentity`）；本机直连这条路根本不经过那三处。
于是 `pref.sessionId`、`pref.provider`、角色设定这些"派生读取"的写入全部蒸发，
`replaceMessages()` 第一句 `if (!pref.sessionId) return;` 就再也不会往服务端写东西。

**修法**：`loadWho()` 成功之后，若本机清单为空就把服务端报回的这个人记进清单
（新增 `ensureIdentityFromMe`，写入仍只走 `addIdentity` 这一个出口）。清单里已有人的时候
一个字都不动——多身份切换、5 条上限、退出回落那些事都建立在"清单只由那三处写"之上。

**为什么安卓不需要跟改**：原生整屏的闸门是 `Prefs.isAuthed = token.isNotEmpty() &&
currentEntry() != null`，"服务端认得人而本机没记人"这一格在原生进不去，它会先看到登录面。
这条判定是读代码得出的静态结论，不是真机跑出来的。

**判据**：`tests/test_web_pwa.py` 末尾 5 条在 node 里真跑仓库那份
`loadWho → ensureIdentityFromMe → touchIdentity → pref 的写入口 → ensureSession`。
把修复那一行摘掉，其中 2 条（指针存活、第二条消息不再另开会话）立刻红；
另外 3 条是护栏（清单已有人的时候不许动、认不出人时不许凭空造身份、
`me` 缺 `user_id` 不许炸），它们保持绿才对。
