## 1. Summary

v0.23 定位为「双端补齐版」：把 v0.22 原生 Android 改造遗留的功能差距一次还清（消息编辑/重新生成、会话导出、日程），清零 v0.22 的已知风险（语音输入未真机实测、像素还原未点验），并建立应用内更新的完整闭环（检查→带进度下载→SHA-256 校验→安装，且今后升级不再要求卸载重装）。

不加新功能面、不做新平台、不做 UI 改版。本版的成功标志只有一条：**安卓端与网页版行为 1:1 契约重新成立，且老用户升级到 0.23 零摩擦**。

**假设与裁决**：

## 3. Goal and Success Criteria

**目标**：恢复双端 1:1 契约，消除升级摩擦，清零上版风险。

成功标准（可量化）：
- S1：R1–R3 每项功能，安卓与网页的操作路径、文案、交互逐屏对照通过，差异清单为空。
- S2：v0.22 正式签名用户升级到 v0.23 **不卸载、聊天记录无损**，全程在 App 内完成（≤3 次点击触发下载，含系统安装页授权）。
- S3：语音输入在 ≥2 家不同厂商 ROM 真机（如小米 + 三星或 OPPO）实测可用；不可用机型给出可读状态提示，不静默失败。
- S4：下载包 SHA-256 与 Release 公布值 100% 校验通过后才拉起安装；校验失败绝不进安装页。

## 4. Users and Scenarios

- **U1 安卓日常用户**：想在手机上改提问重问、把重要对话存成文件、看/管自己的日程——现在只有网页版能做，出外场景断档。
- **U2 从 v0.22 起装正式签名包的用户**：以后每次发版都面临「卸载重装」风险；本版起应一次点击完成升级。
- **U3 网页版用户**：不应感知任何回退；本版对网页版以对齐核对为主、改动极少。

## 5. Scope

**In scope**：R1 消息编辑+重新生成（原生）、R2 会话导出（原生）、R3 日程（双端全新统一界面）、R4 v0.22 风险清零、R5 应用内更新闭环。

**Out of scope**：新模型供应商类型、UI 改版、iOS、多端实时同步、增量 OTA 更新、强制更新/灰度、导出的系统分享面板入口（D2 决议推迟至 0.24）、Agent 任务客户端露出（0.24 候选）、feedback 数据后台（0.24 候选）。

**依赖**：GitHub Releases 可达（服务端出网）；Android `REQUEST_INSTALL_PACKAGES` 权限与 FileProvider；系统语音识别服务（厂商差异）。

## 6. Non-Goals

1. 不为安卓单独发明网页版没有的交互或功能（1:1 契约的刚性执行）。
2. 不重构后端任何既有 API；本版后端只允许新增（若有），不允许改语义。
3. 不做断点续传/下载加速——按几十 MB 级 APK 流式设计即可。
4. 不承诺适配所有国产 ROM 的语音服务，兜底是「明确失败提示 + 引导」，不是强行可用。

## 7. User Flow

### 7.1 消息编辑 → 重新生成（安卓，对齐 web app.js 行为）
1. 长按/点击自己发的用户消息 → 出现操作条（编辑、复制…与网页版同集合）。
2. 点「编辑」→ 原地变编辑框（同网页 `.edit-box` 形态），确认提交。
3. 提交成功 → 截断该消息之后的答复链，自动触发重新生成（走既有 SSE 流式）。
4. 异常态：网络失败保留原编辑内容可重试；会话被他人删除（多端场景）→ 提示后会话刷新。
5. 数据面：`PUT /v1/sessions/{id}/messages` 覆盖消息数组（现有语义）。

### 7.2 会话导出（安卓）
1. 会话内点「导出」→ App 调 `POST /v1/sessions/{id}/export-ticket` 拿一次性票据链接（5 分钟有效、单次兑换）。
2. 原生端不走 WebView blob：直接用系统 DownloadManager/自管下载兑换 `GET /v1/exports/{ticket_id}` 存为 Markdown 文件到系统 Downloads，完成后系统「已下载」通知。（按 D2：本版不做分享面板入口，文件可从文件管理器/聊天应用自行取用；分享面板列入 0.24 候选）
3. 空会话点导出 → 提示「当前没有可导出的对话」（与网页文案逐字一致）。
4. 非本人/不存在的会话 → 404 统一口径，不泄露差异。

### 7.3 日程（双端全新统一界面，基准已锁定 D1）
1. 打开「日程」→ 默认今天清单 → 日期选择器（标记有安排的日子，来自 `GET /v1/schedule` 的 `days` 字段）→ 增删改条目 → 保存时整天 `PUT` 幂等替换。
2. 界面为全新统一设计：安卓（Compose）与网页版各出一版同构设计稿（复用现有设计令牌：主面板圆角 18、组头 12.5px、主题配色），评审一次后双端 1:1 实现；旧壳提醒形态不迁移，仅作交互素材参考。
3. 坏日期/离线：后端 400 时显示服务端 detail 原文，不得渲染成「那天确实没安排」。
4. 跨天边界：0 点后进入页面默认取「服务端本地今天」。
5. 双端同时具备同一入口与文案。

### 7.4 应用内更新闭环（安卓）
1. 设置页「检查更新」→ `GET /v1/update/info`（后端代理 GitHub，10 分钟缓存）。发现新版 → 值槽显示「发现新版本 x.y」。
2. 点「立即更新」→ 应用内进度对话框（已收/总字节 + 取消），下载源钉死为**自家后端同源白名单路径**（浏览器/下载器/迅雷不插手）。
3. 下载完成 → 本地计算 SHA-256 与 `apk_sha256`（Release 正文注入）比对：通过才拉起系统安装页；不符则删文件、明确报错。
4. 后端取不到 GitHub → 5xx 带 detail，App 显示「检查更新失败：<原因>」，**绝不伪装"已是最新版"**。
5. 签名纪律：发布 keystore 永久钉住；CI 增加一步「新包签名字节级指纹 = 上一正式版」的守卫，防止再出现要求卸载重装的签名漂移。
6. 首次落地成本：0.22→0.23 这跳仍需人工安装一次 0.23（0.23 起自带闭环），需在 0.23 Release 说明与 App 内公告明示。

## 8. Functional Requirements

### Requirement R1: 安卓原生「消息编辑 + 重新生成」
- User story：作为安卓用户，我希望能修改自己发错/发简的提问并重新获得答复，就像网页版一样。
- Scenario：见 7.1。
- Functional behavior：操作条、编辑框、截断重发、SSE 流式重生成；文案与网页版逐字一致。
- Data/field changes：复用 `PUT /v1/sessions/{id}/messages`，不改后端。
- Edge cases：流式进行中禁止编辑（与网页一致置灰）；编辑后再生成失败 → 回退非流式（沿用 v0.22 已有失败回退逻辑）；超长消息编辑保留换行。
- Acceptance criteria：
  1. 与网页版逐屏对照，操作步数、文案、动画节奏一致。
  2. 编辑提交后旧答复消失、新答复流式出现，历史刷新后状态一致（数据落服务端）。
  3. 断网提交 → 可重试且不丢编辑内容。
- Priority：P0

### Requirement R2: 安卓原生「会话导出」
- User story：作为安卓用户，我希望把一次对话保存为 Markdown 文件到手机，方便留档与分享。
- Scenario：见 7.2。
- Functional behavior：export-ticket 签发 → 原生兑换下载 → 文件落系统 Downloads（本版不含分享面板，D2 决议）。
- Data/field changes：无新后端字段；原生 `Api.kt:175` 已有签发调用，补 UI 与下载链路。
- Edge cases：票据 5 分钟过期未兑换 → 自动重新签一次，仍失败则报错；用户拒绝存储/通知权限 → 文件仍可存 App 私有目录并提示路径。
- Acceptance criteria：
  1. 导出文件与网页版导出内容逐字节一致（同会话同参数）。
  2. 空会话、无权限、断网三条异常路径均有专属可读提示。
  3. 导出不产生第二个可访问 URL（票据单次性由后端保证，App 不缓存票据）。
- Priority：P0

### Requirement R3: 「日程」双端全新统一实现
- User story：作为用户，我想在 App 里查看和编辑我某一天的安排清单，两端看到的完全一样。
- Scenario：见 7.3（界面基准已按 D1 锁定为全新统一设计）。
- Functional behavior：日视图清单 + 有安排日期标记 + 整天幂等保存；双端同构设计稿一次评审。
- Data/field changes：仅对接现有 `GET/PUT /v1/schedule`。
- Edge cases：400 错误必须展示 detail 而非空清单；跨天 0 点后进入页面默认取「服务端本地今天」。
- Acceptance criteria：
  1. 统一设计稿经评审定稿后，双端逐屏对照实现一致。
  2. 任一端修改，另一端刷新即一致（同源数据）。
  3. 坏日期请求显示服务端原文错误，不渲染空态。
- Priority：P0

### Requirement R4: v0.22 残留风险清零（真机验证专项）
- User story：作为首发用户，我装到的包应该已经在真实手机上被验证过，而不是"构建机说没问题"。
- Functional behavior：语音输入（安卓 SpeechRecognizer + Web Speech API）在 ≥2 厂商 ROM 真机录音实测；像素级还原度对照网页版逐屏点验；权限异常机型走「状态条提示去系统设置」兜底。
- Acceptance criteria：
  1. 真机测试矩阵（机型 × ROM × 语音可用结果）留档，随 Release 附页。
  2. 发现的 UI 还原差异逐条修复或显式记入「已知差异」清单，不允许沉默。
  3. 无法适配的机型给出可执行指引（设置路径原文），不崩溃、不静默。
- Priority：P0（验证类，不新增功能）

### Requirement R5: 应用内更新闭环（下载→校验→安装→签名守卫）
- User story：作为老用户，我希望点一下"立即更新"就在 App 内完成升级，永远不再被要求卸载重装。
- Scenario：见 7.4。
- Functional behavior：迁移 `plan-inapp-update-20260923.md` 方案到原生 App——`/v1/update/info` 消费、同源 APK 下载器（进度回调 + 临时文件 + 改名）、`core/ApkDigest` SHA-256 校验、极简 FileProvider 只暴露 `ai-assistant-*.apk`、原生进度对话框；CI 发布正文确保 `APK-SHA256` 行；新增签名指纹守卫步骤。
- Data/field changes：无业务数据变化；`/v1/release/latest`、`/v1/update/info` 后端已存在，仅核对响应字段够用。
- Edge cases：AC-4「后端取不到 GitHub 不得伪装已最新」；下载中途取消清理临时文件；用户拒绝「安装未知应用」授权 → 引导到系统设置后返回可重试；商店渠道（未来）不劫持该链路。
- Acceptance criteria（含原方案 AC 全量迁移）：
  1. v0.22 正式签名用户装上 0.23 后，检查 0.24 测试包时可全 App 内完成升级，聊天记录无损。
  2. 篡改/残包（人为改动 1 字节）→ 校验失败拒装并删文件。
  3. 非白名单主机或错误路径的下载地址 → 判定 UNUSABLE，不发起下载。
  4. CI 在签名指纹与上一正式版不一致时红。
- Priority：P1

## 9. Data and Permission Requirements

- 新增 Android 权限：`REQUEST_INSTALL_PACKAGES`（更新安装）；导出复用既有通知/媒体权限策略。
- 敏感纪律：更新通道仅同源 + 精确路径白名单；导出链接不落日志、不进剪贴板历史之外的持久存储。
- 无新增用户数据字段；日程/导出/编辑全部复用既有服务端存储。

## 10. Acceptance Criteria（版本级出口条件）

1. S1–S4 四条成功标准全部有证据关闭（对照截图、测试矩阵、升级实测录屏）。
2. CI 全绿（后端测试、原生构建、正式发布六条流水线沿用 v0.22 基线）。
3. 双端 1:1 差异清单为空或全部经评审接受。
4. Release 说明包含：0.22→0.23 最后一跳手动安装的明确指引。

## 11. Rollout and Changelog Notes

- 节奏：功能冻结后先出 0.23-beta 给本机/真机验证（R4 依赖实物设备），再打 tag 走 CI 正式发版（沿用 v0.22 流水线）。
- 网页版随服务端部署即生效，无独立发布动作；更新闭环对用户的首次价值兑现发生在 0.23→0.24 那一跳，Release 文案按此叙述。
- Changelog 草稿要点：新增（日程、原生编辑重发、原生导出、App 内一键更新）、修复（语音权限误报兜底、还原度差异）、注意（本跳需手动装一次）。

## 12. Risks and Open Questions

| 风险 | 等级 | 缓解 |

| 厂商 ROM 语音服务不合规，适配无底洞 | 中 | 限定验证矩阵 2 机型 + 兜底指引即止（见 Non-Goal 4） |
