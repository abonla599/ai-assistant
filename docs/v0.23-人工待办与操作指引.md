## 〇、先纠正一个会卡住所有人的发现（本轮实测）

**线上网页版现在跑的是旧前端，去线上点验会得到无效结论。**

| 来源 | `app.js` 字节数 | sha256 前缀 | 含 `saveSchedule`（日程保存）| 含 `ensureIdentityFromMe`（本轮修的缺陷）|
|---|---|---|---|---|
| 公网 `https://ai.fenever.xyz/app/app.js` | 132,473 | `1f9ff5e5` | 否 | 否 |
| 本机 `http://127.0.0.1:8000/app/app.js`（`run_backend.exe`）| 132,473 | `1f9ff5e5` | 否 | 否 |
| 仓库 `backend/app/web/static/app.js`（`main`）| 147,961 | `386260d4` | 是 | 是 |

两份线上产物逐字节相同、且都比仓库旧——因为运行中的服务是 PyInstaller 打包的 EXE，
前端目录在打包时被打进产物（`run_backend.spec` 的 `datas`），**改仓库文件不会让它自己变新**。
所以「产品 + QA 在浏览器上点验 R1/R2/R3」这一条，在重新打包上线之前无法执行；
要么走下面第 2 节的本地隔离实例（实测过，几分钟），要么走第 8 节的正式部署（有停服窗口）。

**一条我没能证到的事，别当成已证**：后端 API 是不是也落后，从公网判断不了——
`AUTH_MODE=enforced` 下任何 `/v1/...`（哪怕路径根本不存在）都先吃 401，
路由存不存在对外是同一个样子。要确认只看一个地方：`C:\Users\34426\ai-assistant\data\backend.log`
里那次启动的时间，以及 `dist\run_backend\run_backend.exe` 的构建时间。
前端这一侧之所以能断定，是因为静态文件直接给了字节数和哈希。

本轮顺手读了这两个时间，结论已经很清楚：`dist\run_backend\run_backend.exe` 的 mtime 是
**09-26 08:13**、构建戳 `version.txt` 写着 **`v0.22`**，而仓库这份 `app.js` 是 **09-26 18:01** 改的——
那个 EXE 里装的是今天上午的、不含日程/编辑/导出的前端。它同时意味着：
现在这个线上实例的「设置 → 关于」显示的服务端版本是 0.22。

顺带一条同类顺序坑：`docs/安装部署指南.md` 步骤 4 明确「版本号唯一的真来源是 git tag」，
构建戳靠 `git describe --tags --abbrev=0`。远程当前 tag 是 **v0.22**——
现在重建 EXE，「设置 → 关于」显示的服务端版本会是 0.22，而代码其实含 0.23 的功能。
要版本显示也对得上，先打 beta tag（见第 7 节）。

## 二、H1 · D1 门禁四格怎么签（10 分钟内可完成）

**为什么必须你做**：这四格问的是"口味"和"可执行性"，不是"有没有实现"——
`docs/v0.23-阶段0/T0.1-设计稿说明与评审定稿记录.md` 里那四行至今是「待审」：
令牌复用（无新色值/新圆角档）、双端同构性（同 class 结构）、Compose 可执行性（18dp/54px 与现有 tokens 对位）、
异常口径（400 与空态互斥）。我在实现期已经把"能被代码钉死的部分"钉死了（色值集合差、文案逐条同串、
「今天」只从服务端来），评审要推翻这些会先让测试变红；但"是不是你想要的最终观感"没有判据能替你回答。

**准备一个能点验的网页实例**。先说清一件事，否则你会在生产数据上做实验：
源码版起的服务把运行时数据挂在**它自己所在的那棵仓库根**的 `data\`
（`backend/app/core/paths.py::data_root()`：先按 cwd 向上找 `backend/app/main.py`，
找不到就退回"本文件向上三层"）。在本机直接跑下面这条，它写的就是线上同一份 `data\`——
日程那一格尤其明显，保存是真往服务端整日替换的。

**干净做法（推荐，就是把九份可变数据指到临时目录）**——这套变量形状就是
`backend/tests/conftest.py` 用来隔离测试数据的那一套，本轮 R1/R2/R3 取证跑的是同一个形状：

```powershell
$d = "C:\Users\34426\ai-assistant\_local_verify\review-data"
$env:SESSION_DB_PATH   = "$d\sessions.json"
$env:USERS_DB_PATH     = "$d\users.json"
$env:PROVIDERS_DB_PATH = "$d\providers.json"
$env:TASKS_DB_PATH     = "$d\tasks.json"
$env:USAGE_DB_PATH     = "$d\usage.json"
$env:SCHEDULE_DB_PATH  = "$d\schedule.json"
$env:UPLOAD_DIR        = "$d\uploads"
$env:CHROMA_DB_PATH    = "$d\chroma_db"
$env:AUTH_MODE         = "disabled"
$env:AUTH_COOKIE_SECURE = "0"
cd C:\Users\34426\ai-assistant\backend
C:\Users\34426\ai-assistant\venv\Scripts\python.exe -m uvicorn app.main:app --port 8127
```

浏览器开 `http://127.0.0.1:8127/app/` → 设置 → 日程。
（已实测这条起得来：起来后 `/app/app.js` 回 **147,961 字节 / sha256 前缀 `386260d4`**，
即仓库最新那份；线上 EXE 的是 `1f9ff5e5`，两者不是同一个东西。点验完 `Ctrl+C` 停掉。）
注意 `AUTH_MODE=disabled` 只是为了省掉登录，界面与线上一致；换人视角那一格（日程草稿跟着身份走）
在有头浏览器里用真账号才证得到。

要看 400 那一格（本轮已在上面那个隔离实例上实测，服务端原文照抄）：

```js
// devtools 控制台，逐条试
fetch('/v1/schedule?day=abc').then(r => r.json())
fetch('/v1/schedule?day=2026-13-01').then(r => r.json())
fetch('/v1/schedule').then(r => r.json())
```

| 请求 | 状态 | 服务端原文 / 返回 |
|---|---|---|
| `GET /v1/schedule?day=abc` | 400 | `日期要写成 YYYY-MM-DD` |
| `GET /v1/schedule?day=2026-13-01`（格式对、日历上没有）| 400 | `日期不存在：2026-13-01` |
| `PUT /v1/schedule`，body `{"day":"2026-13-01","items":[]}` | 400 | 同上那句「日期不存在」 |
| `GET /v1/schedule`（不传 day）| 200 | `{"day":"2026-09-26","items":[],"days":[]}` |

**界面判据（这就是评审第四格要签的东西）**：出现上面任一 400 原文时，界面上**不得同时**
出现「这天还没有安排」；只有最后那条 200 空清单才允许渲染空态。

**四格各自的判法**（对着 `docs/v0.23-阶段0/T0.1-日程设计稿-双端同构.html` 看）：

1. **令牌复用**——只问一句：实现里有没有哪个色/圆角是稿子里没有的新东西。已代查：无（`test_schedule_ui_contract.py` 做集合差）。你只需确认**稿子本身**的间距/字号是你想要的最终态。
2. **双端同构性**——浏览器 devtools 里看 `#scheduleGroup` 下的结构，与 `android-native/.../ui/ScheduleUi.kt` 的层级对照；两端 class/角色名一致即可签。
3. **Compose 可执行性**——这条只能真机判（18dp 圆角、54px 行高在手机上是否偏挤/偏松），配合 H3 的包一起做；没有真机之前这一格保持待审是诚实的。
4. **异常口径**——上面那个 400 试验做一遍，确认"错误态"和"空态"不同时出现。

**回填位置**：那张表的「结论」列写 `通过` / `改：…`，「签署」写你的名字，「日期」写 `2026-09-26`。
把结论一句话回给我即可，我改文件并把改动挂回测试。

## 四、H3 · 怎么拿到"和 main 一模一样"的可装包（不用等发版）

本机没有 Android SDK，Kotlin 只能在 CI 编译，所以真机验证的包只能从 Actions 取：

1. 打开 `https://github.com/abonla599/ai-assistant/actions/workflows/build-native-apk.yml`
2. 右侧 **Run workflow** → 分支选 `main` → 绿色 **Run workflow**（约 4–6 分钟）
3. 跑完后进入那次 run，底部 **Artifacts** 里下载 **`ai-assistant-native-debug`**
   （内含 `app-debug.apk`，约 9 MB）
4. 传到手机安装即可

> 为什么不能直接用现成的旧包：最近一次产出是 run `36231113186`（commit `16c4fd6c`，08:53 UTC），
> 不含本轮之后的合并点；真机点验要的是"和远程主干一致"的包，所以要点一次 Run workflow。
> 这一步我代不了：`workflow_dispatch` 需要仓库写权限的 token，本机没有 `gh` 也没有凭据。

debug 包足够跑：语音、权限、还原度点验、日程、编辑/重生成、导出落盘。
**不够跑**：升级闭环 U-1/U-3/U-8（要求正式签名 + Release 正文含 `APK-SHA256:` 行），见 H7/H8。

## 七、H7 · 打 tag 之前有一格硬卡点：`versionName` 还是 0.22

**这不是可选优化，是会直接红的**：`android-native/app/build.gradle` 目前写着
`versionCode 23` / `versionName "0.22"`，而 `release-apk.yml` 的第一步就叫
**Check tag matches versionName**（从 `build.gradle` 里 `sed` 出 `versionName` 与 tag 比对）。
所以现在 `git tag v0.23 && git push origin v0.23` 的结果是 Release 流水线第一步失败。

正确顺序（我可以执行到第 3 步，第 1 步的取值和第 4 步的"发"要你一句话）：

1. 你定：**beta 版本号叫什么**（建议 `v0.23-beta.1`），以及 `versionName` 写 `0.23-beta.1` 还是 `0.23`。
2. 我改 `build.gradle`（`versionName` + 需要的话 `versionCode` 递增），跑测试、合并、推送。
3. 我打 tag 并推送（`git tag -a <名字> -m "..."` → `git push origin <名字>`），`Release Android APK` 自动跑：
   构建 → 正式签名 → **SIGNATURE DRIFT 守卫** → 建 Release → 往正文追加 `APK-SHA256: <64hex>`。
4. 流水线全绿后你才说"发"，我打正式 `v0.23`。

签名相关**不用重做**：v0.22 已经是正式签名发布，仓库那四个 Secret
（`APK_KEYSTORE_BASE64` / `APK_KEYSTORE_PASSWORD` / `APK_KEY_ALIAS` / `APK_KEY_PASSWORD`）在位。
只在两种情况需要动：换 keystore（此时守卫会红，按 `docs/APK正式签名落地指引.md` 与
`vars.SIGNATURE_GUARD_EXEMPT` 的豁免流程走，**豁免动作本身必须你来点**，它会在 repo audit log 留痕）；
或你选了"新包指纹"作为一次有意轮换。

## 八、H8 / H9 · 发版与"让线上跟上"的两段路

**H9 网页版上线**（`docs/安装部署指南.md` 的七步，顺序不能换）：

```powershell

cd C:\Users\34426\ai-assistant\backend
..\venv\Scripts\python.exe -m pytest tests/ -q

# 1b 提交/上线前扫密钥

# 2 数清楚现在有几份后端在跑（多于一条 LISTENING 先搞清是谁，别双写同一批 data\*.json）
```
